# 03. 읽기 복제본은 많을수록 좋은가?

## 책의 맥락과 질문

책 p.7–9는 주 DB의 쓰기와 복제본의 읽기를 나눈다. 복제본 증가가 동기화 시간·비용을 얼마나 늘리는지, 조회 병렬성이 항상 이득인지 구분해야 한다.

## 1. 복제본 수만큼 순서대로 기다리는 구조는 아니다

비동기 복제에서는 주 DB가 모든 복제본 반영을 기다리지 않고 커밋할 수 있다. 복제본들은 변경 로그를 받아 처리한다. 동기 복제는 설정한 복제본의 확인을 기다리므로 개수·확인 단계·거리·느린 노드가 지연에 영향을 준다. ‘모든 복제본’을 기다리는지는 설정에 따라 다르다. [PostgreSQL 복제](https://www.postgresql.org/docs/current/warm-standby.html)

## 2. 기다리지 않아도 복제 비용은 있다

로그 전송량, 네트워크, 연결, 복제본 저장 공간이 늘어난다. 복제본에서는 로그 적용과 읽기 쿼리가 자원을 사용한다. 무거운 읽기 때문에 반영이 늦어지거나 DB에 따라 쿼리가 취소될 수도 있다. 계단식 복제로 직접 전송 부담을 나눌 수 있지만 추가 전달 지연과 장애 경로가 생긴다.

각 복제본의 지연, 적용 속도, 조회 지연, 리소스 사용량을 측정한다. 과거 상태를 오래 붙잡은 복제본 때문에 로그 보존량이 증가하는 설정도 살핀다.

## 3. 처리량과 단일 쿼리 속도는 다르다

독립적인 조회를 분산하면 동시 처리량을 늘리고 대기열을 줄일 수 있다. 하지만 쿼리 하나가 자동으로 복제본 여러 대에서 병렬 실행되는 것은 아니다. 캐시 적중률, 데이터 크기, 주 DB와의 통신 등으로 증가 효과가 제한될 수도 있다.

## 4. 오래된 읽기를 허용할지 요청별로 정한다

주문 생성 직후 복제본에서 주문 내역을 읽으면 아직 안 보일 수 있다. 이때 최신성이 필요한 요청을 주 DB로 보내거나 해당 변경의 적용을 확인한다. 단순히 ‘몇 초 동안 주 DB 읽기’는 복제 지연의 상한을 모르면 보장 수단이 아닌 경험적 완화책이다.

복제본 승격 시에는 이전 주 DB의 쓰기 차단과 연결 전환도 필요하다. 복제본이 여러 개라는 사실만으로 자동 장애 전환과 무손실이 보장되지는 않는다.

## 내 말로 정리

복제본 추가는 읽기를 나누는 수단이며 비용과 최신성을 함께 평가한다. 비동기 복제를 여러 대로 늘린다고 쓰기 지연이 같은 비율로 늘지는 않지만 자원 비용과 운영 복잡성은 생긴다.
