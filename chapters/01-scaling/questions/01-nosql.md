# 01. NoSQL은 왜 낮은 지연시간·대용량 저장·규모 확장에 유리하다고 할까?

## 책의 맥락과 질문

책 p.5는 낮은 지연시간이나 대용량 저장 등이 필요한 경우 비관계형 DB를 고려할 수 있다고 설명한다.

- RDB보다 어떤 이유로 응답이 빠를 수 있을까?
- 데이터가 많으면 RDB는 무엇이 어려울까?
- NoSQL은 왜 규모 확장이 간편하다고 할까?

## 먼저 구분할 것

**NoSQL은 하나의 구현 방식이 아니다.** 키-값, 문서, 와이드 컬럼, 그래프 DB를 모두 같은 성능 특성으로 설명할 수 없다. 여기서는 키 기반 접근과 분산 저장을 중심으로 설계한 DynamoDB 같은 시스템을 대표 예로 사용한다.

RDB도 기본키 단건 조회는 빠를 수 있고, 샤딩이나 분산 SQL로 수평 확장이 가능하다. 비교 대상은 단순히 SQL 문법 유무가 아니라 **데이터 모델, 접근 패턴, 일관성·내구성 조건, 분산 기능**이다.

## 1. 낮은 지연시간: 요청 하나에 필요한 일을 줄일 수 있다

예를 들어 사용자 프로필과 설정을 조회한다고 가정한다. 정규화한 RDB에서는 여러 테이블을 조인할 수 있다. 문서 DB에서는 함께 조회하는 정보를 하나의 문서로 저장해 한 번에 가져올 수 있다. 이렇게 미리 조회 형태에 맞춰 저장하면 조인이나 여러 번의 왕복을 줄일 여지가 있다.

하지만 RDB도 조인 없이 저장하거나 적절한 인덱스를 사용할 수 있다. NoSQL도 전체 스캔, 큰 문서, 여러 파티션 조회가 필요하면 느려질 수 있다. 비정규화는 중복 저장과 여러 사본 갱신이라는 비용을 만든다.

일부 제품은 더 약한 읽기 일관성을 선택해 조정 비용을 줄일 수 있다. 반면 강한 일관성이나 여러 항목에 걸친 트랜잭션을 사용하면 비용이 달라진다. “NoSQL은 트랜잭션이 없어서 빠르다”거나 “메모리에 저장하므로 빠르다”는 설명은 일반화할 수 없다.

DynamoDB 공식 문서의 낮은 지연시간 설명도 **기본키를 지정하는 단일 항목 작업의 평균 서비스 지연시간**이라는 조건이 있다. 애플리케이션이 느끼는 시간에는 네트워크, 연결 설정, 재시도 등이 더해진다. 평균만으로 p99를 보장할 수도 없다. [AWS 지연시간 문서](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/TroubleshootingLatency.html)

## 2. 대용량 저장: 데이터를 여러 서버에 나누어 담는다

한 서버에 데이터가 계속 쌓이면 디스크뿐 아니라 인덱스의 크기, 메모리 적중률, I/O, 백업과 복구 시간도 문제가 된다. 서버 한 대를 키우는 수직 확장에는 장비 한계와 비용 문제가 있다.

데이터를 여러 파티션으로 나누면 저장 공간과 처리 부하를 분산할 수 있다. 예를 들어 사용자 ID로 분산하면 각 서버가 전체 중 일부만 담당한다. 단, 키가 고르게 분포해야 하고 요청이 특정 사용자에게만 몰리지 않아야 한다. AWS도 파티션 키와 보조 인덱스 전반에 활동을 고르게 분산하도록 설명한다. [AWS 파티션 키 설계](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-design.html)

여기서 **복제본을 늘리는 것과 저장 용량을 확장하는 것은 다르다.** 전체 데이터를 복제하면 각 서버가 여전히 전체를 담아야 하며 총 저장 비용은 늘어난다. 샤딩은 원본 데이터를 나누므로 서버별 부담을 줄인다. 샤드별 복제를 함께 적용할 수도 있다.

RDB도 샤딩할 수 있다. 다만 단일 DB에서 자연스럽던 조인, 외래키, 유일성, 트랜잭션을 여러 샤드에 걸쳐 유지하려면 추가 설계가 필요하다. 분산 SQL은 이를 지원할 수 있지만 서버 간 통신과 조정 비용까지 사라지는 것은 아니다.

## 3. 규모 확장이 간편한 이유: 분산 기능과 데이터 모델의 조합

단순히 “스키마가 유연해서” 확장이 쉬운 것은 아니다. 일부 분산 NoSQL은 처음부터 다음 기능을 제품에 포함한다.

1. 키로 데이터가 있는 파티션을 찾는다.
2. 용량이나 부하 증가에 맞춰 파티션을 추가·분할한다.
3. 데이터를 재배치하고 요청을 적절한 위치로 전달한다.
4. 복제와 장애 복구를 관리한다.

DynamoDB는 저장 공간이나 설정 처리량 때문에 필요한 추가 파티션을 자동으로 관리한다. 이런 운영 기능을 서비스가 제공하므로 애플리케이션 개발자가 직접 분산 저장 계층을 구현하는 부담이 줄어든다. 모든 NoSQL이 같은 수준의 자동화를 제공하는 것은 아니다. [AWS 파티션과 데이터 분산](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.Partitions.html)

또한 조회와 변경이 같은 키 주변에서 끝나도록 모델링하면 서버 간 조정이 줄어든다. 독립적인 사용자 1만 명의 데이터를 나누기는 비교적 쉽지만, 전 세계 요청이 하나의 재고 숫자를 동시에 바꾸는 문제는 서버 추가만으로 풀리지 않는다. 한 키에 부하가 집중되는 핫키·핫파티션에는 여전히 처리 한계가 있다. [AWS 부하 분산 설계](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/bp-partition-key-uniform-load.html)

## 한계와 반례

| 조건 | 기대하는 이점 | 함께 고려할 비용 |
| --- | --- | --- |
| 키로 조회할 대상을 바로 지정 | 조회 범위와 통신 감소 | 예측하지 못한 검색에는 인덱스·다른 저장소 필요 |
| 관련 데이터를 함께 저장 | 조인·왕복 감소 | 중복과 갱신 정합성 |
| 여러 키로 부하를 고르게 분산 | 저장·처리 용량 확장 | 핫키, 재분배, 운영 비용 |
| 여러 파티션에 걸친 변경을 줄임 | 조정 비용 감소 | 복잡한 업무 규칙을 모델링하기 어려울 수 있음 |

## 내 말로 정리

NoSQL이라서 무조건 빠르거나 데이터가 더 많이 들어가는 것이 아니다. 일부 NoSQL은 정해진 접근 패턴에 맞춰 작업을 단순하게 만들고, 데이터를 분산하는 기능을 제공하기 때문에 낮은 지연시간과 확장성을 얻기 쉽다. 그 이점은 쿼리 자유도와 분산 조정 비용 등과 함께 평가해야 한다.
