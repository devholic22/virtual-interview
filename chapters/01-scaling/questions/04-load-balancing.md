# 04. 정적·동적 부하 분산은 어떻게 다른가?

## 책의 맥락과 질문

책 p.6–7의 로드 밸런서를, 사용자가 언급한 『주니어 백엔드 개발자가 반드시 알아야 할 실무 지식』의 정적·동적 분류와 연결한다. 후자의 원문은 제공되지 않아 표현을 대조하지 않았으며 아래는 개념 설명이다.

## 분류 기준

현재의 부하 지표를 배정 판단에 반영하는지로 구분한다. 설정이 파일에 고정되어 있다는 사실과 정적 알고리즘이라는 개념은 다르다.

| 분류 | 방식 | 판단 기준 | 한계 |
| --- | --- | --- | --- |
| 정적 | 라운드 로빈 | 순서 | 요청별 비용 차이 반영 어려움 |
| 정적 | 고정 가중 라운드 로빈 | 미리 정한 비율 | 실제 부하와 다를 수 있음 |
| 정적 | IP 해시 | IP 해시 값 | NAT로 같은 IP 사용자 집중 가능 |
| 동적 | 최소 연결 | 활성 연결 수 | 연결 수와 처리 비용은 다름 |
| 동적 | 응답시간 기반 | 관측한 응답시간 등 | 측정 지연·노이즈·급격한 변화 |

NGINX의 최소 연결은 활성 연결 수를 참고하며, 서버 CPU를 직접 측정한다는 뜻은 아니다. [NGINX 부하 분산](https://nginx.org/en/docs/http/load_balancing.html)

## 헬스 체크·세션 고정과의 관계

헬스 체크는 요청을 보낼 수 있는 서버인지 확인하고, 알고리즘은 정상 서버 중 어디로 보낼지 고른다. 정적 방식도 장애 서버를 제외할 수 있다. IP 해시 등으로 세션을 고정할 수 있지만 웹 서버의 상태 외부화나 장애 복구를 대신하지는 못한다.

## 동적 방식도 항상 우월하지는 않다

관측값이 늦게 도착하거나 다수의 배정자가 같은 서버를 동시에 고르면 부하가 쏠릴 수 있다. 짧고 비슷한 요청은 단순 분산으로 충분할 수 있고, 작업 시간 차이가 큰 요청은 연결·진행 중 작업 수 같은 지표가 더 유용할 수 있다. 지속 연결·HTTP 다중화에서는 연결 수가 요청 수를 잘 대변하는지도 확인한다.

## 내 말로 정리

핵심은 ‘동적이면 좋다’가 아니라 배정 지표가 실제 부하를 얼마나 잘 나타내는가다. 웹 서버 분산을 개선해도 하나의 DB 재고 행에 집중되는 병목은 따로 해결해야 한다.

## 후속 질문

- 연결 수, 진행 중 요청 수, 지연시간 중 무엇이 작업 부담을 나타내는가?
- 서버 장애와 과부하를 각각 어떻게 감지하는가?
- 지표가 오래되거나 누락되면 어떤 방식으로 배정하는가?
